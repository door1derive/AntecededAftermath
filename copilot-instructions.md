# The discussion so far.

This project has been started with the help of Windows copilot.

We started off by establishing the desire to create an OpenGL project. Blender files can be thought of as the starting point for the project. An export python script will be created to place the mesh data into geometry arrays inside a C++ header. We discussed exporting vertex, normal, color, material id, and uv coordinates. I have a script that does this on another account, but it's a pretty big mess. It might contain errors with regard to how it pads arrays to keep data arrays parallel. It might be better to just start from scratch.

I have those arrays sorted according to which triangle a particular vertex belongs to. It was suggested that that array can be condensed to reduce the amount of data stored and passed to OpenGL. That idea appeals to me because I will probably be pushing the amount of geometry that OpenGL can handle on my computer.

A basic engine format was discussed. Basic chrono functionality sets up the framerate at 60 frames per second. A game loop first checks for user input. If none is received, the game functions are run. I was previously using a Linux system and calling X11 to check user input. But I want the game to be compatible with Windows, Mac, and Linux systems, so I would like to switch to STL. The game will use basic WASD and mouse look controls. I have functions that track those in another project, door2u/nodefeat, so I won't need help with that. My camera is basically an object holding a location vector and three unit vectors for each axis. Copilot suggested we add clipping planes to the camera and I think that's a good idea. The game will hold off on implementing collisions for now. Node Feat used a path system that tracked which triangle region the character was in. That worked well for me because it was lightweight, stable, and could be used to restrict player movement and determine the player's proximity to other objects. The system is not quite finished but it's close. I will also want to implement a raycast system by tracking bounding boxes that follow targets and sort their minimum and maximum into a game-wide array. Then the ray itself could be separated into x, y, and z to quickly determine the next intersecting bounding box. If an intersection with a bounding box was detected, then maybe the ray could be rotated around the object and tested with a precalculated array of AABB around each object polygon. If a polygon bounding box is detected, then a ray/plane intersection could be checked. Other systems will mostly be simple (except one discussed below). Lighting can be completely avoided for the time being. Flat and normal shaders will suffice for the development process. I might like to use geometry that is somewhat detailed to compensate. I will avoid rigging and skinning by separating character limbs into individual objects and animating their rotation around their parents on a timer. For sound it would probably be sufficient if the program could load and simultaneously play a single sound format, like WAV.

One thing that was not yet discussed was a system for simulating how electromagnetic radiation interacts with objects. I want to get somewhat serious about these calculations and attempt to simulate how materials of different sizes and composition affect the path of radiation from a variety of sources, intensities, and frequencies, according to known physical equations. So I plan to do a fair amount of research to try to find databases and equations, and I will asking a lot of questions about how to implement these equations into the game. I would like to implement some kind of system that would show how radiation might look if it was able to be visualized. That might work using a particle system, an animated mesh that becomes more opaque with depth, a combination of the two, and making the addition of something else. I want to be able to test heavy materials like lead or tungsten, or composite materials. I also would like to simulate what would happens to objects with an inconsistent density. I want to attempt to simulate what happens when radiation encounters a charged surface, water, extreme angles, and combinations of all of these. A basic system can be set up at first which is expanded upon over time.

One mechanic I would like to implement is a robot that autonomously explores the facility according to a manual program set by the player. They could be lazy and set something simple like "turn left when hitting a wall". Then the player could investigate while the robot maps out the facility. The robot could be interrupted and driven manually at any time, which could eventually be successful in mapping out the majority of the facility. But a specific area could be designed which prevents it from being entered by simple algorithms. The hidden area could be ignored for the majority of the level, but becomes significant at some point. So I will want the facility to be expansive, but somehow avoid having to walk forever to get from one place to another, so maybe like a cart system, and a handful of scout bots to strategically distribute.

Some basic plot and thematic elements were discussed. Copilot suggested the word Aftermath and I added Wormhole, to suggest a consequence that precedes an effect. I also like that the game might be math heavy, but has an ominous implication. I don't want the user to require math knowledge, but I'm hoping the game might have the ability to enlighten the player, and I, on ideas that are perceived as abstract. Copilot suggested naming the research facility where scientists are killed by radiation "Helios", and I like that idea.

Several other concepts were discussed, such as project organization, workflow, and sustainability. Copilot suggested the prompt "Create a C++17 OpenGL camera class using GLFW input and glm matrices", and I agree. The only issue I have is that I want to make the game is compatible across the three major operating systems.

So far there is one python script at Blender/facility_builder/floor.py, which needs to be separated into multiple libraries and python scripts. This script generates a couple of floors for rooms of the research facility. The idea of the script is to generate a facility procedurally rather than to define it explicitly. It only generates two room floors, but it's a solid foundation, no pun intended. The floors are made of beveled triangles that combine into hexagons which I wanted to be a little bit interesting and a little bit unsettling. The location of rooms are set by vectors that wind around from the starting point. The scale of the vectors and the space between rooms can be edited to adjust the scale of the facility as a whole. I wanted to next create a set of functions that boolean the triangles based on any given reference point, so that rooms of other shapes could be generated.
